MD5 Length Extension with Chosen-Pad Obstacle

CTF Writeup · Hackademics Forum CTF 2025 · Author: Daysa

TL;DR

When a server prints bus_id = md5(secret) and lets you append user-controlled bytes before secret[:N], sending the MD5 internal padding for length=52 as your input converts the query into a classic length-extension construction. With 1000 queries you collect the 53 unique hashes (one per N=0..52), anchor N=0 by extending bus_id, then recover the secret byte-by-byte in ~13K predictions.

The Challenge

A small TCP server hands out a 32-hex-char bus_id at the start of each session and lets you submit up to 1000 "obstacle" queries. Each one returns:

md5(secret + obstacle + secret[:N]).hexdigest()

where secret = urandom(52) and N = randint(0, 52) is chosen independently per query. Your job is to recover the 52-byte secret and submit it back as hex.

Hint: The server prints bus_id = md5(secret).hexdigest() in the opening banner. That's not decoration — it's the input you need for a length-extension attack.

The Vulnerability

This is a textbook MD5 length extension vulnerability, but the trick is identifying which obstacle activates the construction. The vulnerable formula is:

md5(secret + obstacle + secret[:N])

If obstacle equals the MD5 internal padding for a 52-byte message:

obstacle = b'\x80' + b'\x00' * ((56 - (52 + 1) % 64) % 64) + struct.pack('<Q', 52 * 8)
        = 12 bytes: 80 00 00 00 a0 01 00 00 00 00 00 00

then the server computes:

md5(secret + pad + secret[:N])

which is the canonical length-extension construction. The attacker can predict md5(secret + pad + X) for any X without knowing secret, only needing bus_id = md5(secret) and len(secret) = 52.

Why the random N doesn't help

At first glance the random N ∈ [0, 52] looks like a defense: with 53 possible outputs, you can't tell which hash corresponds to which state. But once you force the server into the length-extension construction:

  • Each of the 53 possible N values produces a distinct, deterministic hash for a fixed obstacle = pad.
  • In 1000 queries you'll see each of those 53 hashes ~19 times.
  • The hash for N = 0 is trivially identified: it's md5_extend(bus_id, 52, b"") = md5(secret + pad).
  • The remaining 52 hashes are exactly md5(secret + pad + secret[:N]) for N = 1..52, one per byte-pattern of secret.

The Attack

Phase 1 — Collect the 53 hashes

Send the MD5 padding as obstacle 1000 times. The server returns 53 unique hashes (one per N=0..52), each repeated ~19 times. Build a set of unique hashes for the next phase.

Phase 2 — Anchor N=0

Apply length extension on bus_id with an empty suffix:

h_N0 = md5_extend(bus_id, 52, b"")

This is exactly what the server returns when N=0. Remove it from the pool. You now have 52 remaining hashes that correspond to N=1..52.

Phase 3 — Recover the secret byte-by-byte

For each byte position k = 0..51:

  1. Try all 256 candidate values c.
  2. Build the candidate suffix suffix = secret_recovered[:k] + bytes([c]).
  3. Predict md5_extend(bus_id, 52, suffix).
  4. If the prediction is in the remaining pool → that's the correct byte.
  5. Remove the hash from the pool and continue with byte k+1.

Total predictions: 256 × 52 = 13,312. After all 52 bytes, the pool is empty (all 53 hashes accounted for), confirming full recovery.

The Length Extension Primitive

A minimal MD5 length-extension function (no external crypto library, ~50 lines):

def md5_extend(known_hash_hex, known_length, suffix):
    glue = b'\x80' + b'\x00' * ((56 - (known_length + 1) % 64) % 64)
    glue += struct.pack('<Q', known_length * 8)
    state = struct.unpack('<4I', bytes.fromhex(known_hash_hex))
    total = known_length + len(glue) + len(suffix)
    new_msg = suffix + b'\x80' + b'\x00' * ((56 - (len(suffix) + 1) % 64) % 64)
    new_msg += struct.pack('<Q', total * 8)
    cur = state
    for i in range(0, len(new_msg), 64):
        cur = md5_compress(cur, new_msg[i:i+64])
    return struct.pack('<4I', *cur).hex()

You only need md5_compress (the 64-round function) — no need to reimplement the full MD5 hash from scratch.

Verification

I tested the attack end-to-end against a local simulated server with urandom(52):

  • N=0 anchored correctly ✓
  • 52 bytes recovered byte-by-byte ✓
  • 0 hashes remaining at the end ✓

Where length extension has been exploited in production

API token signing (Flickr, ~2009) — Flickr's API used MD5(secret + params) as a request signature. An attacker who intercepted one signed request could forge signatures for arbitrary new requests, escalating privileges or accessing other users' data. Root cause: treating hash(secret + data) as a MAC.

MAC schemes in web frameworks (~2008) — CVE-2008-2380 affected multiple PHP applications that computed hash(secret + user_data) for session integrity. An attacker could append arbitrary data to the session, bypassing the integrity check entirely.

MIT Kerberos RC4-HMAC-MD5 (CVE-2025-3576) — when RC4 is preferred over AES in Kerberos, message integrity checks use RC4-HMAC-MD5. The MD5 checksum structure allows an attacker to forge GSSAPI-protected messages, potentially tampering with authentication tokens.

Embedded devices (CVE-2024-56516) — recent CVEs in hashlib-style libraries that expose raw md5(secret) outputs while accepting user-controlled suffixes (e.g., firmware signature schemes, IoT device provisioning tokens).

Affected pattern (the dangerous code shape)

# ❌ DANGEROUS — vulnerable to length extension
signature = md5(secret + user_controlled_data)
if signature == provided_signature:
    authorize_action()

# ✅ SAFE — uses HMAC, designed against length extension
import hmac, hashlib
signature = hmac.new(secret, user_controlled_data, hashlib.md5).hexdigest()
if hmac.compare_digest(signature, provided_signature):
    authorize_action()

Why HMAC is safe

HMAC wraps the hash function twice with the secret padded to block size: H((K ⊕ opad) || H((K ⊕ ipad) || message)). The internal construction breaks the Merkle-Damgård continuation that length extension exploits. SHA-3 and BLAKE2 also have different internal constructions that are immune.

Defense checklist (for auditors)

  • 🚩 Red flag: any code using hash(secret + user_data) or hash(secret || user_data) as a MAC
  • 🚩 Red flag: exposing raw md5(secret) or sha1(secret) outputs in HTTP responses, logs, or API tokens
  • ✅ Use HMAC for any user-controlled data + secret construction
  • ✅ Use SHA-256 or SHA-3 if you need collision resistance beyond MAC properties
  • ✅ Use signed tokens (JWT with HS256/RS256) instead of rolling your own
  • ✅ Constant-time comparison (hmac.compare_digest) to avoid timing attacks

What I Learned

Post-mortem honesty: I spent ~5 hours exploring wrong vectors (timing attacks, race conditions, brute force against the random N) before recognising that the construction is exactly the canonical length-extension setup. The sub-agent that I spawned with "fresh eyes" found it in minutes. The lesson: when the server hands you a hash and lets you append arbitrary data, look for the construction first, not the obfuscation.
