Cracking an MD5 secret byte by byte

CTF writeup · Hackademics Forum 2025 · Author: Daysa

What this is about

The server gives you the MD5 hash of a secret at the start of the game. You also get 1000 chances to ask the server "if I append these bytes to your secret and chop a random prefix off the end, what hash do you get?" If you ask the right question, you can recover the entire 52-byte secret one byte at a time. That's the whole trick.

The challenge in plain English

You connect to a small server. It does three things:

  1. Generates a random 52-byte secret and prints its MD5 hash at the top of the screen (the "bus ID").
  2. Lets you submit up to 1000 messages. For each one it computes md5(secret + your_message + secret[:random_prefix]) where the random prefix is somewhere between 0 and 52 bytes long. It prints the resulting hash.
  3. Asks you to send back the original 52-byte secret in hex. If you get it right, it gives you the flag.

The catch: you only see hashes, never the secret itself. And the random prefix means you don't know exactly which bytes of the secret the server used to compute each hash.

The giveaway: the server literally hands you md5(secret) in the banner. That's not decoration. It's the key to the whole thing.

Why the random prefix doesn't actually help

At first glance the random prefix sounds like a defense. With 53 possible lengths, you can't tell which hash corresponds to which "state" of the server. But there's a specific message you can send that turns the whole thing into a textbook MD5 weakness called length extension.

Here's the idea. MD5 is built in blocks of 64 bytes. When you ask MD5 to hash a message that's not a multiple of 64 bytes long, it automatically pads the message with some extra bytes before processing. The padding looks like this:

\x80  (one byte marking the end of the real message)
\x00 ... \x00  (zero bytes until we hit position 56)
[length of the message, 8 bytes, little-endian]

For a 52-byte message, the padding is exactly 12 bytes: 80 00 00 00 a0 01 00 00 00 00 00 00. And here's the magic: if you feed that padding as your message, then the server computes

md5(secret + padding + secret[:N])

which is the same shape as MD5 doing a "two-part hash": first hashing secret + padding, then continuing from there with secret[:N]. That's the canonical length-extension setup.

The attack in three steps

Step 1 — Collect the hashes

Send the 12-byte MD5 padding (80000000a001000000000000 in hex) 1000 times. The server gives you back 1000 hashes, but there are only 53 distinct ones. That's because the random prefix has 53 possible values (0 through 52), and for each value you always get the same hash.

Throw them all into a set. You're done with the network for now.

Step 2 — Find the N=0 hash

One of those 53 hashes is special: the one where the random prefix was zero bytes. That hash is md5(secret + padding + nothing) = md5(secret + padding).

The nice part: you don't need to know the secret to compute this. You already have md5(secret) from the banner. There's a well-known trick called length extension where, given md5(secret) and the length of the secret (52), you can compute md5(secret + padding + anything) for free. So you compute md5_extend(banner_hash, 52, empty_bytes) and look for it in your set. When you find it, remove it. You now have 52 hashes left, each one corresponding to md5(secret + padding + secret[:N]) for a specific N between 1 and 52.

Step 3 — Recover the secret one byte at a time

Now you have 52 hashes, each of which was generated from the secret. The trick is to brute force each byte sequentially:

  1. For byte 0, try every value from 0 to 255. For each candidate, predict what the hash md5(secret + padding + byte_candidate) would be (using length extension again). If your prediction matches one of the 52 remaining hashes, congratulations — you just found byte 0.
  2. Move to byte 1. Now try every value, but this time your prediction is md5(secret + padding + byte_0 + byte_candidate). Match a hash, lock in byte 1.
  3. Repeat for bytes 2, 3, ..., 51.

You end up doing at most 256 × 52 = 13,312 hash predictions. In practice it's much fewer because most candidates get rejected immediately. When you finish, all 53 hashes should be accounted for. If they are, you have the complete 52-byte secret.

How length extension actually works

MD5 processes data in chunks. After hashing a message, it has an internal "state" — four 32-bit numbers. If you know that state and the length of the original message, you can keep going. Just feed the next chunk of data, and MD5 picks up exactly where it left off.

You don't need to know what the original message was. You just need its hash (which is the final state) and its length. That's why having the banner hash is enough.

For the actual math: MD5's padding scheme is predictable, and the state after hashing secret is the same as the state after hashing secret + padding. So predicting md5(secret + padding + X) for any X is just a matter of running MD5's compression function once more on the next chunk.

The bit that surprised me

The "obvious" answer here is length extension. I had that tool ready from the start. What I missed for hours was the specific input that triggers the attack: the MD5 internal padding itself. Once you feed the padding as your message, the server's computation becomes the textbook length-extension construction, and everything falls into place.

Honest post-mortem: I spent about five hours going down rabbit holes (timing attacks, race conditions, brute force on the random prefix) before recognising that the construction was right there in front of me. A fresh-eyes sub-agent found it in minutes. Lesson: when a server gives you a hash and lets you append data, look at the structure first, not the obfuscation.

Where this matters in the real world

Length extension isn't a toy. It's broken real production systems:

  • Flickr API (2009) used MD5-based signatures for authenticated requests. An attacker who intercepted one signed request could forge valid signatures for arbitrary new requests, escalating their access to other users' data.
  • Multiple PHP webapps (2008) used md5(secret + session_data) as a session integrity check. Attackers could append data to their session and forge a valid hash, bypassing the check entirely.
  • MIT Kerberos (2025) had a related issue: when RC4-HMAC-MD5 was preferred over AES, attackers could forge GSSAPI-protected messages.
  • IoT firmware signing (2024) exposed raw MD5 hashes alongside user-controlled data in provisioning tokens, enabling firmware bypass.

The common thread: every one of these systems used the pattern hash(secret + user_controlled_data) as authentication. The fix is simple — use HMAC instead, which is specifically designed to block this attack. SHA-3 and BLAKE2 are also immune because they don't use the same internal structure as MD5 and SHA-2.

Audit checklist: if you see md5(secret + user_input) or sha256(secret + user_input) used as a signature or MAC in any codebase, it's broken. Replace it with hmac.new(secret, user_input, hashlib.sha256).
