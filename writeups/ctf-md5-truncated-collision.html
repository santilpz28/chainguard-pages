Truncated MD5 Collision

A birthday-style attack against a server that compared only 5 hex characters of MD5 against a random target. The challenge asks the player to "help Mike reach his destination safely" while a 32-character bus identifier rotates every connection — a classic example of why truncated hash comparisons are not security.

Bottom line

The server compares only 20 bits of an MD5 digest against a random target. The full 128-bit hash space would resist brute force for centuries; a 20-bit space can be exhausted in roughly one million trials on commodity hardware. With ~1M SHA/MD5 hashes per second on a modern CPU, the entire attack finishes in under a second per attempt.

Vulnerability

The challenge server exposes a target — a fresh 32-character hex string generated each connection — and asks the player to send back arbitrary bytes (interpreted as a hex string) whose MD5 starts with the same 5 hex characters as the target:

if md5(obstacle).hexdigest()[:5] == bus_id[:5]:
    # success

The full 32-character MD5 has 128 bits of pre-image resistance. The first 5 hex characters carry only 20 bits: a search space of 16^5 = 1,048,576. That space is exhausted by brute force in milliseconds on any modern CPU, with no GPU required.

Why this matters beyond CTFs

Truncated hash comparisons have appeared in production code for decades:

  • Authentication bypass. PHPBB2-era CMS systems occasionally compared substrings of password hashes for "speed". An attacker who found any pre-image whose MD5 prefix matched could log in.
  • Token validation. Several legacy session managers and CAPTCHA systems verified only the first 8–12 hex characters of a token signature.
  • API signature checks. AWS Signature Version 2 used truncated HMACs before being deprecated in 2014 in favor of SigV4.
  • Payment verification. Some legacy payment gateways validated only partial MACs, enabling micro-transaction forgery.

Attack

The exploit is a textbook birthday-style collision search:

  1. Connect to the server and read the bus_id.
  2. Extract the 5-character target (bus_id[:5]).
  3. Generate random byte sequences, compute MD5, and check whether the first 5 hex characters match.
  4. On match, send the matching bytes back as hex. The server converts them with bytes.fromhex(), recomputes MD5, finds a match, and reveals the flag.

The expected number of trials is the search space itself (~1M). On a single CPU core, Python's hashlib.md5 runs at roughly 1–2 million operations per second — so the entire attack finishes in well under a second.

Remediation

  • Compare the full hash. Never slice an authentication primitive. Even 128 bits is the floor for MD5; SHA-256 or SHA-3 are the modern baseline.
  • Use constant-time comparison. hmac.compare_digest in Python, hash_equals in PHP, crypto.timingSafeEqual in Node — these avoid timing side-channels as well.
  • Prefer HMAC over raw hashes. HMAC-SHA256 with a server-side secret defeats offline collision attempts entirely. If the server cannot keep a secret, use Argon2id for password storage.
  • Never rely on MD5 for security. It has been deprecated for cryptographic use since 2004 (NIST SP 800-107). MD5 remains useful for checksums and cache keys — never for authentication or integrity.

Takeaway

The challenge is a clean illustration of an asymmetry that shows up constantly in audits: the full algorithm looks strong (MD5, 128 bits), but the integration pattern is what fails (5 hex chars of comparison). A junior reviewer sees "MD5 — broken, downgrade to SHA-256" and misses the bug. A senior reviewer sees the comparison and stops the engagement. The right primitive in the wrong wrapper is still the wrong primitive.
